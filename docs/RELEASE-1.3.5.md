# 1.3.5：修复休眠时只交给系统排队的分支

## 问题与改动
10月26日日志显示，07:00闹钟到达后，旧版本因设备休眠而只安排系统联网加急任务；直到导出日志都没有实际启动记录。此前将系统接受排队作为放弃前台启动尝试的条件，导致定时执行依赖系统后续调度。

本版删除“仅因休眠而优先排队并返回”的分支。有效定时事件直接申请 dataSync 前台服务，与非休眠时使用相同检测入口。实际前台启动被拒绝、发生系统超时或网络完全无响应时，继续保留已有带 Wi-Fi 条件的系统备用任务。因这些实际失败而写入的当前时段阻断标记仍保留，避免无限重启前台服务；下个时段可重新尝试。

不改变绑定 Wi-Fi、认证协议、已在线即停止、07:00–07:05窗口、停止操作、认证冷却或蜂窝/VPN设置。保留1.3.4后台检测并登录自测。

## 调度状态
- 备用任务被系统接受时记录“已接受排队，尚未确认启动”，持久记录排队时间、时段、配置版本和任务令牌。
- 任务真正取得执行权并启动 TaskRunner 后，另记“已实际启动”及等待时长；重复任务拿不到执行权时不会误标为启动。
- 应用仍在运行并读取状态时，可以显示仍在排队的等待秒数；超过30秒尚未开始时只补记一次警告。
- 应用下次读取状态、规划计划或接收备用任务时，核对过期排队。未开始且已过时段的任务标记为过期并取消；不发送迟到认证，不覆盖后来成功的检测结果。
- 这不是常驻监控：进程未运行时不会凭空产生看门狗回调，过期信息在下次运行时补记。系统备用任务仍不保证立即执行。

## 安装与验证
直接覆盖安装，不卸载旧版。打开一次确认自动计划仍为07:00–07:05并已开启，然后正常使用。原有后台登录自测仍可使用，但短时熄屏自测不能替代深度休眠后的每日定时验证。次日先导出记录，再手动登录，以保留自动执行的原始结果。
